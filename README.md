# College Event Management and Registration System

A beginner-friendly full-stack college project for publishing campus events, registering students, managing event capacity, and tracking participants.

## Problem and objectives

Colleges may manage technical, cultural, sports, and workshop registrations with separate forms or spreadsheets. This application centralizes event discovery and registration, avoids duplicate registrations, enforces capacity in PostgreSQL, and gives administrators participant reports.

## Users and features

- **Student:** create an account, log in, browse/search events, register, see personal registrations, cancel a registration, log out.
- **Administrator:** create/edit/cancel events, view participant lists, export CSV reports.
- **Security:** bcrypt password hashing, server-signed HttpOnly cookie, role checks on the server, request validation, login/register rate limit, Helmet security headers, PostgreSQL constraints, and atomic capacity checks.

## Technology stack

HTML5, CSS3, Vanilla JavaScript, Node.js, Express.js, Supabase PostgreSQL, Git, and GitHub. Backend npm dependencies are listed in `backend/package.json`.

## Supabase setup

1. Create a project at [Supabase](https://supabase.com/). Save the database project URL and server-side service-role/secret key privately.
2. In the Supabase dashboard, open **SQL Editor** and create a new query.
3. Copy all of `database/schema.sql` into the editor and run it.
4. Open **Table Editor** and verify `profiles`, `events`, and `registrations` exist.
5. In **Project Settings → API** (the label may vary by dashboard version), copy the project URL and the server-side service-role/secret key. Never put this key in frontend code or GitHub.

The SQL enables RLS and grants no direct table access to browser roles. This app uses the privileged key only in the backend, and its Express routes enforce authentication and roles. Do not build a direct-to-database browser client with this key.

## Configure and run

Open a terminal in the project root, then:

```bash
cd backend
npm install
```

Copy the example environment file:

**Windows PowerShell:**

```powershell
Copy-Item .env.example .env
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

**macOS/Linux:**

```bash
cp .env.example .env
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Edit `backend/.env` and set:

- `PORT=3000`: local web server port.
- `NODE_ENV=development`: use `production` only when deployed over HTTPS.
- `SUPABASE_URL`: URL of your own Supabase project.
- `SUPABASE_SERVICE_ROLE_KEY`: server-only privileged key from your Supabase project.
- `JWT_SECRET`: paste the long random string generated by Node.js (at least 32 characters).
- `COOKIE_NAME`: name of the session cookie; keep the provided value.

Do not put quotes around values unless required, and never commit `.env`.

Start the server from `backend/`:

```bash
npm run dev
```

Expected output: `CampusConnect running at http://localhost:3000`. Open [http://localhost:3000](http://localhost:3000). The frontend is served by Express, so API requests use the same origin. To stop the server, press `Ctrl+C`.

## Create the first administrator

1. Create a normal account through the app.
2. In Supabase **Table Editor → profiles**, find that account.
3. Change its `role` from `student` to `admin`.
4. Log out and log in again so the new role is reflected in the signed session.

Only a trusted project owner should promote an administrator. The public registration endpoint always creates `student` accounts; never accept a role from the browser.

## API overview

All responses are JSON. Authentication uses an HttpOnly cookie; do not manually store a session token in localStorage.

| Method | Path | Access | Purpose |
|---|---|---|---|
| GET | `/api/health` | Public | Health check |
| POST | `/api/auth/register` | Public, rate limited | Create student account; body `{name,email,password}` |
| POST | `/api/auth/login` | Public, rate limited | Log in; body `{email,password}` |
| GET | `/api/auth/me` | Logged in | Current account |
| POST | `/api/auth/logout` | Public | Clear session cookie |
| GET | `/api/events` | Public | List published events and counts |
| GET | `/api/registrations/mine` | Student/admin | Current user's registrations |
| POST | `/api/registrations` | Logged in | Register; body `{event_id}` |
| DELETE | `/api/registrations/:id` | Owner only | Cancel own registration |
| GET | `/api/admin/events` | Admin | List all events and counts |
| POST | `/api/admin/events` | Admin | Create event |
| PATCH | `/api/admin/events/:id` | Admin | Edit event fields |
| DELETE | `/api/admin/events/:id` | Admin | Cancel event and active registrations |
| GET | `/api/admin/events/:id/participants` | Admin | List active participants for an event |
| GET | `/api/admin/registrations` | Admin | All registration report rows |

Event create/update body: `{title,category,description,event_date,venue,capacity,fee}`. Categories are `Technology`, `Cultural`, `Sports`, `Workshop`, or `Other`. `event_date` must be a future ISO-compatible date/time. Capacity is 1–10000; fee is 0–100000 INR. Event status is changed to `cancelled` rather than physically deleting historical data. API errors use `{ "error": "Human-readable message" }`.

## Database design

- `profiles`: account identity, name, unique email, password hash, role.
- `events`: event details, capacity, fee, status, creator and timestamps.
- `registrations`: one row per student/event, status and creation time.
- `register_for_event(...)`: PostgreSQL function locks the event row and atomically checks status, date, duplicates and capacity before registering.

The server uses the Supabase service-role key, which bypasses RLS; therefore server authorization is essential. The SQL revokes direct access from `anon` and `authenticated` roles and exposes no browser table policies. Do not expose the server key. For a production deployment, consider Supabase Auth, managed secrets, stronger audit logging, and an authorization design aligned with your deployment.

## Use and manual tests

1. Open the home page and check event cards load from PostgreSQL.
2. Register a student using a valid email and a password of at least eight characters.
3. Log in and register for a future event; the personal registration should appear after refresh.
4. Try registering twice for the same event; the second request should be rejected.
5. Cancel a registration and verify the available seat count updates.
6. Promote a test account to `admin` using the dashboard, then log in again.
7. Create and edit an event, inspect its participant CSV, and export the all-registration report.
8. Test invalid form fields, full event capacity, expired sessions, and student attempts to call admin endpoints.
9. Test at desktop and mobile viewport widths.
10. Check `http://localhost:3000/api/health` for `{ "status": "ok", ... }`.

## Troubleshooting

- **Missing environment variables:** confirm `.env` is inside `backend/` and restart the server after editing it.
- **Database/API error:** verify the project URL/key, that `schema.sql` ran successfully, and that the Supabase project is available.
- **401 response:** log in again; the HttpOnly cookie may have expired.
- **403 response on admin:** promote the account in the trusted Supabase dashboard and log in again.
- **No events shown:** create a future event with an admin account; cancelled events are not shown in the public catalogue.
- **Port in use:** change `PORT` in `.env` and open that port in the browser.
- **Changes not visible:** hard-refresh the browser and inspect the terminal for errors.

## Git and GitHub

Create an empty GitHub repository, then run these commands from the project root:

```bash
git init
git status
git add .
git status
git commit -m "Build college event management system"
git branch -M main
git remote add origin YOUR_GITHUB_REPOSITORY_URL
git push -u origin main
```

Replace `YOUR_GITHUB_REPOSITORY_URL` with the repository URL from your GitHub page. Before committing, confirm `backend/.env` and `node_modules/` are ignored and `.env.example` is included. Never commit real keys, passwords, or student exports. `.gitignore` does not erase a secret already committed: rotate exposed credentials immediately and clean repository history if needed.

## Limitations and future improvements

This is a learning MVP, not a complete production deployment. It does not implement email verification, password reset, payment collection, or automated tests. Admin promotion is a manual trusted-dashboard action. Production use should add HTTPS deployment, automated backups, monitoring, password recovery, audit trails, and a carefully reviewed security model.
